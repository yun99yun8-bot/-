# TRON Monitor V9.4.1 — 0尾区块校准

基于 V8.1.6 稳定采集/Worker/遗漏引擎，重建 AI 决策层。

## V9 核心
- 严格只使用开奖前可见的 1–17 组与此前正式开奖结果。
- 修正旧模型历史序列方向：历史数据为“最新→最旧”，近期窗口、遗漏与转移模型均按正确方向计算。
- 同时运行 long / short / structure17 / transition / omission / binomial 六个候选模型。
- 候选模型权重由过去已锁定且已验证的样本外成绩自动调整，并对小样本做收缩。
- Binomial(7,0.5) 作为简单基准，避免把单3/单4天然高频误认为 AI 规律。
- 每期预测仍在 G20 前持久化锁定；G20 只负责验证，不能反向修改预测。
- ensemble_detail 中保存 V9 权重、候选组件和 rolling-OOS 研究成绩，可继续审计。
- `edgeStatus` 会标记 NO_EDGE / WEAK_EDGE / EVIDENCE；它只是统计证据等级，不代表保证命中。

## 保留
V8.1.6 的 G17 事件锁定、G20 屏障、DB-first、自修复、独立遗漏引擎和 Render Background Worker 架构均保留。

## 部署
Web 与 Background Worker 继续使用同一仓库和 DATABASE_URL。Worker Start Command: `python worker.py`。


## V9.1 多维AI决策中心
- 首页重构为最终综合结论、Top3、多模型预判、真实样本外命中反馈和基准比较。
- 候选模型扩展为17组结构、哈希结构、位置关联、短期、长期、状态转移、遗漏条件、Binomial基础分布。
- 哈希结构只作为开奖前统计特征，不宣称存在可预测公式；真实样本外成绩可增加其探索权重。
- 最近20/100/500期Top1实时反馈仅使用开奖前已锁定并已开奖验证的记录。
- 保留V9.0/V8.1.6的G17/G20生命周期、数据库与遗漏引擎。

## V9.2 验证修正
- 样本外统计只使用 V9 预测记录，且必须能核对 `locked_at <` 目标区块的链上时间；早期版本及不能核实锁定顺序的记录不计入。面板最近20/100/500期与模型成绩采用相同筛选。
- 每个复杂模型在与基础分布相同的已验证期次上计算 Top1 配对优势及抽样误差。至少100个有效样本且优势超过1.64倍抽样误差时才获得额外权重。证据提示为探索性统计，不能当作未来命中保证。
- 历史窗口默认读取最近1000期，和长期模型描述一致。界面展示每个候选模型的有效样本数，移除了未经校准的“一致度”百分比。
- 开发检查：`python -m unittest discover -s . -p 'test_*.py' -v`；生产运行仍使用 `render.yaml` 中相同的 Web/Worker 和 `DATABASE_URL`。

注意：这份包尚未连接用户的线上 PostgreSQL 或 TRON 服务进行集成验证，部署前请检查实时锁定事件与区块时间记录。

## V9.3 单3/单4集中问题
- V9.2 样本不足时基础分布占100%，因此最终排序会退化为单3、单4。V9.3 使用固定且明确标为“探索性”的多维初始权重：基础分布25%、前17组结构20%、历史位置关联15%、短期12%、长期8%、转移8%、遗漏6%、哈希结构6%。
- 验证过的配对优势仍能追加有限权重；没有统计优势时，页面会明确显示“探索性排序”。强烈的当期结构信号能够让单2等进入综合第一位，但不会为了分散结果而强制轮换号码。
- 锁定后的 Top3 显示来自同一个冻结快照的分数和百分比，避免展示旧算法分数。

## V9.3.1 首页“单—”修复
- 首页在展示正式七号码前核算单几；即使缓存或接口的单几字段为空，也从号码尾数重新计算。无有效七号码时显示“待开奖”，不把未知值误显示成开奖结果。
- 新页面刚打开且当期尚未开奖时，从最近已确认的第20组结果恢复上一期的期号、七号码、单几及区块。快速结果接口在当前期尚未开奖时也提供这一回退；当期正式结果出现后仍由新区块覆盖。
- 前端脚本语法、单几为0或字段缺失的渲染路径及现有模型测试已检查；仍需在实际部署环境核对数据库中的历史区块。

## V9.3.2 采集速度
- 第20组快速线程在前17组尚未到齐、且倒计时仍大于12秒时暂停请求尚不存在的目标区块；到第17组或倒计时12秒内立即恢复直接查询。减少与正常采集线程争用共享请求限速器，避免无效请求引发429。
- 支持后端环境变量 `TRON_PRO_API_KEY`；只向 `api.trongrid.io` 发送 `TRON-PRO-API-KEY` 请求头，不暴露给浏览器或其他数据源。未设置时保持原有请求方式。
- `/api/draw` 的 `debug.fastTarget` 新增 `barrierMs`，区分目标取块耗时 `latencyMs` 与开奖前预测锁定耗时。若 `barrierMs` 大，继续排查 G17 提前锁定；若 `latencyMs` 大，检查节点响应与429。
- 区块本身未产生前不能提前取得开奖结果。升级后应在真实线上运行中比较 `latencyMs`、`barrierMs`、429次数和平台显示时间，本地测试无法证明实测提速。

## V9.3.3 首页波色
- 删除首页“本期正式结果已确认”及同一状态栏的提示文字，保留开奖期号、区块、倒计时与七个号码。
- 七个开奖号码改为白底彩色圆形描边：绿波 05、06、11、16、17、21、22、27、28、32、33、38、39、43、44、49；蓝波 03、04、09、10、14、15、20、25、26、31、36、37、41、42、47、48；红波为其余给定的17个号码。
- 新结果到来时按号码重绘，先清除旧波色，避免上期颜色留在下一期。占位号码保持灰圈。

## V9.3.4 单3/单4诊断与全类别显示
- 用固定种子的1500组二项基准模拟复现原模型：Top1 单3为756次、单4为735次，单2仅2次、单5仅7次。该测试检查代码偏置，不是线上命中率或未来预测能力的证明。
- 首页在锁定后展示单0–单7全部相对模型分数，并单独列出分数最高的非3/4类别。它是研究候选，可与正式Top3重合，不额外计入命中。
- 正式锁定预测和样本外评价保持原口径；没有验证证据时不会为了号码分散而强制轮换 Top1。若要改变正式选择策略，应先用真实的已锁定历史记录做逐期回测，评估命中率和覆盖范围。

## V9.4 历史哈希训练
- Background Worker 每5分钟从 `period_groups` 中读取最多2500个已完成期次（约4.5万组）。只把每期1–17组哈希及其单几作为特征，第20组的单几只作训练标签。使用哈希末尾、A–E与数字构成、17组单几结构等低维特征，不记忆完整哈希。
- 按期号先后划分70%训练、15%调参、15%留出验证；至少400个完整期次才训练。留出期次的对数损失和Top1都优于简单基准时，模型快照才加入正式集成预测。否则只显示“未达门槛”，正式预测不增加哈希模型权重。
- 训练和验证在后台进行，保存于 `hash_model_runtime`。第17组锁定时只读取快照，不扫描几万条哈希；预测使用的快照及分数写入本期已锁定记录，保持第20组开奖后不可倒改。
- 首页显示训练样本数、留出验证期数与模型是否入选。此版本仅通过合成数据和代码测试，未接入用户线上 PostgreSQL，因此不能声称已发现哈希的可预测规律或提高命中率。
