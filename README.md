# TRON 一分钟统计监控（v7）

## 本版核心规则
- 每天平台期号固定 `0001`～`1440`，次日重新从 `0001` 开始。
- 每一期内部对应 20 个 TRON 区块进度：`1/20`～`20/20`。
- 20 组不是 20 个开奖期；平台每分钟只增加 1 个期号。
- 第 17/20 组生成“王者归来”统计预判并锁定，第 20/20 组作为正式开奖结果。
- “王者归来”和“历史统计”使用完全不同的预判逻辑。

## 历史统计独立预判
- 只读取已经完成的正式开奖记录。
- 默认读取最近连续 2 期的“单数个数”作为历史模式，例如：`单3 → 单4`。
- 在全部历史记录中寻找相同模式，统计该模式之后下一期出现 `单1`～`单7` 的次数。
- 将次数换算为百分比，`单1`～`单7` 七项全部展示，由用户自行选择。
- 预判结果带目标期号和历史匹配次数。
- 可通过环境变量 `HISTORY_PATTERN_LEN` 修改历史模式长度（默认 2）。

## 时间和区块
- 页面当前时间只显示年月日，例如 `2026-09-24`，不显示时钟。
- 内部使用 `APP_TIMEZONE`（默认 `Asia/Shanghai`）计算期号。
- 2026-09-24 的已验证锚点：`86502288`；平台截图显示每分钟目标区块间隔 20。
- 新日期若没有人工锚点，会根据当前链高估算并标记为未确认。

## Render
Build command:
`pip install -r requirements.txt`

Start command:
`python app.py`

需要配置：
- `TRON_PRO_API_KEY`
- `APP_TIMEZONE=Asia/Shanghai`
- 可选 `DB_PATH`
- 可选 `POLL_SECONDS`
- 可选 `BLOCK_ANCHOR`
- 可选 `HISTORY_PATTERN_LEN`

历史数据需要持久化存储；Render 若没有 Persistent Disk/PostgreSQL，重新部署或实例重启可能导致 SQLite 数据丢失。
